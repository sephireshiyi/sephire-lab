# Markdown 渲染：通用权衡框架

> **性质**：项目无关的思维框架，不绑定 Sephire Lab 的具体选型。用来分析"任何把 Markdown 渲染成页面"的系统——博客、论坛、评论、wiki、文档站、笔记软件。
>
> 本项目的具体落点见 `../decisions/blog-mdx-pipeline.md`；本文档是它背后的"为什么"。将来加评论、做 wiki、写文档站时回看本文档。
>
> **更新历史**：
> - 2026-06-06：初版。从一次"MDX 技术选型为什么是这样"的讨论中提炼。

---

## 0. 核心洞见（先记这两句）

1. **Markdown 渲染链路是分层的，可替代性逐层不同**——真正"换不掉"的只有底层 AST 引擎生态，上层工具大多可换。
2. **决定一切架构差异的最大变量是「信任」**：内容是你自己写的，还是陌生人写的？这一条几乎单独决定了其余所有选择。

---

## 1. 分层视图：链路的 6 层

把任何 Markdown 渲染系统竖切成 6 层职责，立刻能看清哪层粘、哪层松：

| 层 | 职责 | 可替代性 | 说明 |
|---|---|---|---|
| **L1 解析引擎** | Markdown 文本 → AST → HTML | 🔴 低（生态级） | 换引擎=放弃整个插件生态，代价极高 |
| **L2 要不要"增强"** | 能否在内容里嵌组件（MDX）/原始 HTML | 🟡 中 | 取决于需求，不需要就别加 |
| **L3 框架胶水** | 引擎怎么接进 Next/Astro/… | 🟢 高 | 纯接线，等价选项一堆 |
| **L4 frontmatter 解析** | 裁出元信息 | 🟢 高 | 等价库随便换 |
| **L5 校验** | 元信息合法性 | 🟢 高 / 可选 | 可换可不要 |
| **L6 代码高亮** | 代码块上色 | 🟢 高 | 换插件的事 |

**关键**：只有 L1 是"粘"的。原因是 L1 有**生态引力**——见 §2。

---

## 2. L1 的三大引擎家族（JS 生态）

| 引擎家族 | 特点 | 代表使用者 |
|---|---|---|
| **unified / remark / rehype** | 基于 AST + 插件化，扩展性最强，但重、有学习曲线。几百个 `remark-*`/`rehype-*` 插件（数学、图表、目录、脚注…）都假设你用它 | MDX、Astro、Docusaurus、Gatsby |
| **markdown-it** | 也插件化，但更轻更快、API 更直观 | VitePress、Discourse 论坛、很多评论系统 |
| **marked / 其他** | 极轻极快，插件少 | 要求最小依赖 / 最快解析的场景 |

**"可替代性低"的真正含义**：不是某个包换不掉，而是一旦进了某个引擎家族（尤其 remark），那棵 AST 树的**生态引力**让你很难跨家族迁移——因为会丢掉整个插件生态。**家族内部一切可换，跨家族换代价大。**

---

## 3. 决定性变量：信任（blog vs forum）

这是整个框架的核心。**内容是谁写的**，几乎单独决定其余所有架构选择：

```
作者自己写（博客/文档）        陌生人写（论坛/评论/UGC）
──────────────────────       ──────────────────────────
内容可信                      内容不可信（可能是攻击载荷）
↓                            ↓
可以允许原始 HTML              绝不能允许原始 HTML / JS
可以用 MDX 嵌组件              绝不能执行用户的 JSX/JS
build 时编译一次              运行时实时编译（内容随时新增）
不需要消毒（sanitize）         必须激进消毒
```

### 为什么 UGC 必须消毒、禁 MDX

MDX/原始 HTML 会**执行**内容里的脚本。允许陌生人写 = 允许任何人在你站点上跑任意代码 = **XSS（跨站脚本攻击）**，灾难级漏洞。例如一条"评论"：

```html
<script>把所有访客的登录 cookie 发到攻击者服务器</script>
```

不消毒就渲染 → 所有看到它的人账号被盗。

### 消毒（sanitization）是什么

UGC 管线必然多一步：用 `rehype-sanitize` / `DOMPurify` / `sanitize-html` 这类工具，**只保留白名单内的安全标签**（`<b>` `<a>` `<code>`…），剥掉 `<script>`、`onclick`、危险属性。这是 UGC 系统和作者博客**最本质的架构区别**。

> **推论**：一个项目"要不要做评论"不只是产品决策，它直接引入一整块安全复杂度（运行时渲染 + 消毒 + 受限 Markdown 子集）。

## 4. 渲染时机：成本落在哪

| 时机 | 谁付出成本 | 适合 | 代价 |
|---|---|---|---|
| **Build 时（SSG）** | 构建机器 | 内容固定（博客文章） | 内容一变要重新 build |
| **服务器运行时（SSR）** | 服务器算力 | 内容随时变（论坛新帖） | 每次请求都要算 |
| **客户端** | 用户浏览器（下载 JS） | 需要实时交互（在线编辑预览） | 往浏览器发渲染程序，首屏变重 |

**成本守恒**：渲染这件事总得有人扛——要么 build 慢、要么服务器累、要么用户下载大。选时机本质是"把成本推给谁"。

## 5. 通用权衡清单（8 条轴）

设计 / 分析任何 Markdown 嵌入系统，都可以用这 8 条轴去拆：

| # | 轴 | 两端 | 影响 |
|---|---|---|---|
| 1 | **信任** ⭐ | 自己写 ↔ 用户写 | 用户写→必须消毒、禁 HTML/JSX/MDX。最重要 |
| 2 | **渲染时机** | build ↔ 服务器 ↔ 客户端 | 成本推给谁；内容多动态就越靠右 |
| 3 | **扩展性** | 纯文本格式 ↔ 可嵌组件 | 只要加粗表格→纯 Markdown；要嵌互动→MDX |
| 4 | **性能落点** | build / 服务器 / 浏览器 bundle | 同 §4 |
| 5 | **功能丰富度** | 极简 ↔ 全功能 | 数学(KaTeX)/图表(mermaid)/脚注/表格 要不要 |
| 6 | **生态绑定** | remark / markdown-it / marked | 要海量插件→remark；要轻快→其他 |
| 7 | **类型/校验** | freeform ↔ schema 校验 | 内容多怕写错→上 zod 类；随手写→不要也行 |
| 8 | **写作方式** | git 文件 ↔ 网页编辑器 ↔ 输入框 | 文件→gray-matter；数据库/远程→运行时字符串编译 |

**用法**：先在第 1 条（信任）定位，它会把后面几条的取值范围大幅收窄。

## 6. 真实系统怎么做（对照）

### 作者写的（博客 / 文档站，build 时，免消毒）

| 站点/工具 | 引擎 | 时机 |
|---|---|---|
| Astro | 内置 Content Collections + remark/rehype | build |
| Docusaurus | MDX（remark/rehype） | build |
| Next.js 博客 | @next/mdx 或 Velite | build |
| Hugo（Go） | Goldmark | build |
| Jekyll（Ruby） | kramdown | build |
| VitePress | markdown-it | build |

### 陌生人写的（论坛 / 评论，运行时，强制消毒）

| 平台 | 引擎（大致） | 时机 |
|---|---|---|
| GitHub | cmark-gfm（GFM 标准源头，C 实现） | 运行时 |
| Discourse | markdown-it（服务端+客户端） | 运行时 |
| Discord | 自定义极简 Markdown 子集 | 客户端 |
| Reddit / Stack Overflow | CommonMark 系实现 | 运行时 |

> 具体实现会随版本变（如 Reddit 历史上用过自研 snudown）。**记模式，别记包名。**

## 7. Sephire Lab 在这张表上的落点

把本框架套回本项目，解释为什么 `../decisions/blog-mdx-pipeline.md` 的选型是那样：

| 轴 | 本项目取值 | 推出的选择 |
|---|---|---|
| 信任 | 自己写 | **免消毒**、可用 MDX |
| 渲染时机 | build（SSG） | @next/mdx build 时编译 |
| 扩展性 | 要嵌组件 | 用 MDX 而非纯 Markdown |
| 性能落点 | 压在 build | 客户端零渲染 JS |
| 功能 | 中等（暂不上数学/图表） | remark-gfm 够用 |
| 生态 | remark | rehype-pretty-code / rehype-slug 等 |
| 校验 | schema 校验 | gray-matter + zod |
| 写作 | git 里的 .mdx 文件 | gray-matter 读文件 |

**结论**：那套链路不是唯一解，而是"个人博客"这组约束在 8 条轴上的**自然落点**。换成论坛，同一张表会推出完全不同的一套（markdown-it + 运行时 + 强制消毒 + 禁 MDX）。

> **未来触发点**：哪天给本项目加**评论功能**，第 1 条（信任）翻转 → 立刻需要引入运行时渲染 + 消毒 + 受限 Markdown，那是另一套子系统，不要复用博客的 MDX 管线。
