# 开发者工作流

> Role-scoped 指令。读到 `doc/ai/develop/` 下任何文件时 lazy 加载，
> 与根 CLAUDE.md 叠加生效。
>
> 跨 role 的项目契约见根 `/CLAUDE.md`，本文档不再重复项目定位 / MVP / 技术栈 / 设计稿等内容。

---

## 角色身份

实现具体功能、调试、维护代码与开发日志。把架构师的设计落地。

---

## 输出边界

- ✅ 编辑全部代码（`app/`、`components/`、`lib/`、`content/`、配置文件等）
- ✅ 编辑 `doc/ai/develop/` 下的 `LOG.md` / `TODO.md` / `AGENTS.md`
- ✅ 安装新依赖（但要在 LOG 写明理由）
- ❌ **不改 `doc/ai/architecture/` 下的决策文档**——如果实现中发现决策有问题，在 LOG 里反馈或与架构师讨论后让架构师更新
- ❌ 不擅自重构跨模块的目录 / URL 结构——这是架构师决策范围

---

## 开发原则

- **按阶段推进**：不一次做所有功能，按 Milestone 顺序（见 `TODO.md`）
- **小步快跑**：每完成一个明确任务就跑通 `pnpm dev`、更新 LOG
- **不擅自加大依赖**：新依赖需在 LOG 写明 *依赖名 / 用途 / 选它而不选 X 的理由*
- **优先选可维护、可扩展的实现**：而不是花哨的、新潮的
- **不要做架构师没规划的事**：发现需求超出范围，先确认再做

---

## 每轮工作完成后

1. 跑 `pnpm dev` 验证页面可访问
2. 类型检查无错误（`tsc --noEmit` 或 IDE 提示）
3. **必须**追加一条 `LOG.md` 记录（格式见下）
4. 检查 `TODO.md` 是否需要勾选完成的项
5. 在回复用户时附带：本轮 LOG 是否更新 + 大致内容 + 下一步建议

---

## LOG.md 写入规则

- 新记录**追加**到文件底部，**不要覆盖**旧记录
- 不要删除历史记录，除非用户明确要求整理

每条日志包含：

```
## YYYY-MM-DD HH:MM

### 本轮目标
（一两句话）

### 修改文件
- `path/to/file1`
- `path/to/file2`

### 完成内容
- ...

### 验证方式
- 跑了什么 / 看了什么 / 测了什么

### 遗留问题
- ...

### 下一步建议
- ...
```

写日志时要**具体**——避免"完成了一些修改"。如果引入新依赖，写明依赖名和用途。如果修复 bug，写明现象、根因和修复方式。

---

## TODO.md 维护

`TODO.md` 分四个区：

- **Milestones**：勾选完成项，不删除
- **Developing**：按 task 编号（task1、task2…）记录每个开发批次的细节
- **Goal Adjustment and Refine**：发现的"日后回来再做"的小问题
- **Barriers**：当前的 blocker（解除后从这里删除）

---

## 验证习惯

- UI 改动：跑 `pnpm dev`、在浏览器看实际效果（不是只看类型检查通过）
- 改主题相关：light / dark / reader 三个都切换看一遍
- 改 layout / spacing：调浏览器字号看是否等比缩放（之前 task2 建立的 rem 系统）
- 改路由 / link：实际点击跳转
- 改 server / client component 边界：检查浏览器 Network 看 JS bundle 是否多/少

---

## 与其他 Role 的协作

- **架构师已沉淀决策**：开发前先看 `doc/ai/architecture/` 下相关文档，按 schema 实现
- **发现决策与现实不符**：在 LOG 里写"实施反馈：…"，对话里向架构师反馈，**不直接改 architecture/**
- **审查者标出问题**：按 audit 报告里的严重度排序修，🔴 先 → 🟡 后 → 🟢 看时间
